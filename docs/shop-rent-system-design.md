# 收租系统设计方案

## 一、背景与目标

### 背景
项目已有完整的股市交易系统，角色拥有灵石资产。需要新增店铺收租玩法，作为角色的被动收入来源，与股市形成互补的经济系统。

### 目标
1. **被动收入**：每 30 分钟 tick 自动产出租金，角色可收取
2. **成长体系**：店铺可通过装修、空间扩展、升级等级提升租金产出
3. **策略权衡**：装修可随时升降级（降级 60% 回收），但消耗 1 次 tick 租金，玩家需权衡装修等级与面积的关系
4. **资源消耗**：装修和扩空间消耗灵石，形成灵石回流机制
5. **初始赠送**：角色创建即获一间黄级书籍店铺，降低门槛
6. **复用 tick 机制**：不新建定时器，复用现有股市 tick 调度器

---

## 二、核心概念

### 2.1 店铺基础属性

| 属性 | 说明 |
|------|------|
| 店面类型 | 丹药 / 矿材 / 书籍 / 灵植 / 法器 / 餐饮 |
| 面积（㎡） | 各类型初始面积不同，空间扩展可增加 |
| 装修等级 | 黄 / 玄 / 地 / 天（基础装修品质，非店铺评分） |
| 升级等级 | 非负整数，从 0 开始，通过收租积累提升 |
| 空间阵法扩展次数 | 非负整数，每次扩展增加内部空间容量 |
| 待收租金 | 累积未领取的灵石数 |
| 累计收租次数 | 用于驱动升级等级提升 |
| 最后装修 tick | 记录最近一次装修的 tick ID，用于跳过该 tick 租金 |

### 2.2 初始状态

角色创建时自动获得 **1 间黄级·书籍店铺**，面积 20 ㎡，升级等级 0，空间扩展 0 次。

### 2.3 初始店铺补领（容错）

若角色创建时因异常未分配初始店铺，玩家在店铺页面可**免费领取**一间黄级·书籍店铺（限领一次，不扣灵石）。

### 2.4 店铺数量限制

**每种店面类型最多持有 1 间**，不可重复拥有同类型店铺。角色最多持有 6 间店铺（6 种类型各 1 间）。

### 2.5 店铺购买成本

书籍店铺为免费赠送的初始店铺，其他 5 种店铺需要花费灵石购买：

| 店面类型 | 购买成本（灵石） | 初始租金/tick | 回本 tick 数 |
|----------|----------------|--------------|-------------|
| 餐饮 | 50,000 | 15 | 3,333 |
| 法器 | 80,000 | 18 | 4,444 |
| 矿材 | 120,000 | 20 | 6,000 |
| 丹药 | 150,000 | 22.5 | 6,667 |
| 灵植 | 200,000 | 25 | 8,000 |

购买成本基于「初始面积 × 租金价值 × 类型溢价」综合定价。玩家在股市资金和店铺投资之间做资源分配决策。

## 三、面积模型

### 3.1 各类型初始面积

| 店面类型 | 初始面积（㎡） | 说明 |
|----------|--------------|------|
| 灵植 | 50 | 培育区 + 灌溉区，最大面积 |
| 矿材 | 40 | 矿石、金属存放，需要承重空间 |
| 法器 | 35 | 陈列展示 + 仓储 |
| 丹药 | 30 | 丹炉 + 药材存放 |
| 餐饮 | 25 | 堂食 + 后厨 |
| 书籍 | 20 | 书卷占地小，最小面积 |

### 3.2 空间阵法扩展（空间折叠术）

每次扩展固定增加 **10 ㎡**，扩展次数无上限。扩展总费用由**空间阵法费用**和**扩展面积装修费用**两部分组成。

```
空间阵法费用 = 基础费用 × 2^(扩展次数) × 装修等级系数
扩展面积装修费用 = 装修单价（灵石/㎡） × 10 ㎡
扩展总费用 = 空间阵法费用 + 扩展面积装修费用
```

| 参数 | 值 |
|------|-----|
| 基础费用 | 50 灵石 |
| 扩展次数指数 | 2^n（第 1 次 2^0，第 2 次 2^1，第 3 次 2^2...） |
| 装修等级系数 | 黄 1x / 玄 1.5x / 地 2x / 天 3x |
| 装修单价 | 黄 10 / 玄 30 / 地 60 / 天 100 灵石/㎡ |

> **说明**：扩展次数从 0 开始计数，即第一次扩展时 `扩展次数 = 0`，第二次 `扩展次数 = 1`，以此类推。

**各装修等级扩展费用表（单位：灵石）：**

| 扩展次数 | 黄级 (×1) | 玄级 (×1.5) | 地级 (×2) | 天级 (×3) |
|----------|-----------|------------|-----------|-----------|
| 第 1 次 | 空间 50 + 装修 100 = **150** | 空间 75 + 装修 300 = **375** | 空间 100 + 装修 600 = **700** | 空间 150 + 装修 1000 = **1150** |
| 第 2 次 | 空间 100 + 装修 100 = **200** | 空间 150 + 装修 300 = **450** | 空间 200 + 装修 600 = **800** | 空间 300 + 装修 1000 = **1300** |
| 第 3 次 | 空间 200 + 装修 100 = **300** | 空间 300 + 装修 300 = **600** | 空间 400 + 装修 600 = **1000** | 空间 600 + 装修 1000 = **1600** |
| 第 4 次 | 空间 400 + 装修 100 = **500** | 空间 600 + 装修 300 = **900** | 空间 800 + 装修 600 = **1400** | 空间 1200 + 装修 1000 = **2200** |
| 第 5 次 | 空间 800 + 装修 100 = **900** | 空间 1200 + 装修 300 = **1500** | 空间 1600 + 装修 600 = **2200** | 空间 2400 + 装修 1000 = **3400** |

## 四、装修模型

### 4.1 装修费用（基于面积）

天地玄黄仅表示基础装修品质档次，不是店铺评分。装修费用与**面积**直接挂钩：

```
装修费用 = 基础单价（灵石/㎡） × 当前面积
```

| 装修等级 | 单价（灵石/㎡） | 书籍 20㎡ | 灵植 50㎡ |
|----------|----------------|----------|----------|
| 黄 | 10 | 200 | 500 |
| 玄 | 30 | 600 | 1,500 |
| 地 | 60 | 1,200 | 3,000 |
| 天 | 100 | 2,000 | 5,000 |

### 4.2 动态装修规则

- **可随时升级或降级**装修等级
- **降级返还 60%**：按（当前等级单价 - 目标等级单价）× 当前面积 × 60% 退还灵石
- **装修消耗 1 次 tick**：发起装修的当前 tick 无法获得租金，新等级从下个 tick 生效
- 升级等级和累计收租次数在装修过程中**保持不变**

**降级退款示例：**
- 玄级→黄级（30㎡）：(30 - 10) × 30 × 60% = **360 灵石退款**
- 天级→地级（50㎡）：(100 - 60) × 50 × 60% = **1,200 灵石退款**

### 4.3 装修中的状态管理

新增字段 `last_decorate_tick_id`：
- 发起装修时记录当前 tick ID
- 下一 tick 处理租金时，若 `last_decorate_tick_id == 当前 tick_id`，跳过该店铺租金计算
- 之后自动恢复正常收租

## 五、租金模型

### 5.1 不同店铺初始租金

| 店面类型 | 初始面积 | 初始租金（灵石/tick） | 说明 |
|----------|---------|---------------------|------|
| 灵植 | 50㎡ | 25 | 培育周期长，产出高 |
| 丹药 | 30㎡ | 22.5 | 炼丹利润高 |
| 矿材 | 40㎡ | 20 | 矿石稳定产出 |
| 法器 | 35㎡ | 18 | 中等收益 |
| 餐饮 | 25㎡ | 15 | 日常消费，稳定偏低 |
| 书籍 | 20㎡ | 10 | 入门店铺，收益最低 |

### 5.2 租金计算公式

```
最终租金 = 初始租金 × 装修等级系数 × 空间阵法加成 × 升级等级加成
```

| 参数 | 值 | 说明 |
|------|-----|------|
| 初始租金 | 见 5.1 表格 | 按店铺类型区分 |
| 装修等级系数 | 黄 1.0x / 玄 2.0x / 地 4.0x / 天 8.0x | 每提升一级翻倍 |
| 空间阵法加成 | 1 + 扩展次数 × 0.5 | 每次扩展 +50% |
| 升级等级加成 | 1 + 升级等级 × 0.1 | 每级 +10% |

**示例计算：**

| 店铺状态 | 计算 | 每 tick 租金 |
|----------|------|-------------|
| 黄级·书籍·0 扩展·Lv.0 | 10 × 1.0 × 1.0 × 1.0 | **10 灵石** |
| 黄级·书籍·3 扩展·Lv.0 | 10 × 1.0 × 2.5 × 1.0 | **25 灵石** |
| 玄级·丹药·0 扩展·Lv.0 | 22.5 × 2.0 × 1.0 × 1.0 | **45 灵石** |
| 玄级·书籍·2 扩展·Lv.2 | 10 × 2.0 × 2.0 × 1.2 | **48 灵石** |
| 地级·灵植·1 扩展·Lv.0 | 25 × 4.0 × 1.5 × 1.0 | **150 灵石** |
| 天级·丹药·3 扩展·Lv.5 | 22.5 × 8.0 × 2.5 × 1.5 | **675 灵石** |

### 5.3 装修等级与面积的策略权衡

面积越大，装修费用越高，但租金产出取决于装修等级而非面积。玩家需要在「扩展空间提升租金」和「控制面积减少装修投入」之间做权衡。

**回本分析（以书籍 20㎡ 为例）：**

| 操作 | 费用 | 每 tick 租金 | 回本 tick 数 |
|------|------|-------------|-------------|
| 初始状态 | 0 | 10 | — |
| 黄→玄 | 600 | 20 | 60 |
| 玄→地 | 1,200 | 40 | 60 |
| 地→天 | 2,000 | 80 | 50 |

**回本分析（以丹药 30㎡ 为例）：**

| 操作 | 费用 | 每 tick 租金 | 回本 tick 数 |
|------|------|-------------|-------------|
| 初始状态 | 0 | 22.5 | — |
| 黄→玄 | 900 | 45 | 40 |
| 玄→地 | 1,800 | 90 | 40 |
| 地→天 | 3,000 | 180 | 33 |

## 六、升级模型

### 6.1 店铺升级（提升升级等级）

每次收取租金时，根据累计收租次数判断是否触发升级：

```
每 tick 获得的升级经验 = 1
升级所需经验 = 10 × (当前升级等级 + 1)
```

| 升级等级 | 升到下一级所需累计收租次数 |
|----------|--------------------------|
| 0 → 1 | 10 次 |
| 1 → 2 | 20 次 |
| 2 → 3 | 30 次 |
| 3 → 4 | 40 次 |
| ... | 线性递增 |

升级等级不影响装修费用，但通过升级加成系数影响租金产出（每级 +10%）。

---

## 七、租金累积上限

为防止玩家长时间不登录导致一次性获取天文数字租金，设置累积上限：

```
最大累积 tick 数 = 24 小时 / 30 分钟 = 48 tick
```

超过 48 tick 未收取的租金不再累积。

## 九、数据库设计

### 9.1 新增表：`shop_tick`（收租系统独立 tick 表）

```
id                  BigInt (PK, 自增)     -- tick 唯一 ID
tick_hour           DateTime (UNIQUE)     -- tick 对应的小时时间
status              String                -- running / generated / failed
error_message       String?               -- 失败原因
created_at          DateTime              -- 创建时间
finished_at         DateTime?             -- 完成时间
```

> **设计说明**：收租系统拥有独立的 tick 机制，不与股市 tick 混用。由同一调度器触发，但记录在独立表中。

### 9.2 新增表：`shop_detail`（店铺详情表）

```
id                  Int (PK, 自增)        -- 店铺唯一 ID
character_id        Int (FK -> characters.id)  -- 所属角色
shop_type           String                -- 店面类型 (DAN/MIN/BOO/PLT/ART/FBD)
area                Int                   -- 当前面积（㎡）= 初始面积 + 扩展次数 × 10
decoration_tier     String                -- 装修等级 (YELLOW/MYSTIC/EARTH/HEAVEN)
upgrade_level       Int                   -- 升级等级，默认 0
space_expansion     Int                   -- 空间阵法扩展次数，默认 0
pending_rent        BigInt                -- 待收租金（单位：分，与灵石精度一致）
total_rent_collected BigInt               -- 累计已收租金（统计用）
rent_tick_count     BigInt                -- 累计收租次数（升级判断）
last_rent_tick_id   BigInt?               -- 上一次结算的 tick ID（关联 shop_tick）
last_decorate_tick_id BigInt?             -- 最近一次装修的 tick ID（用于跳过该 tick 租金）
created_at          DateTime
updated_at          DateTime
```

> **设计说明**：
> - `area` 字段直接存储当前面积，避免每次计算。扩展空间时同步更新 area + 10。
> - `(character_id, shop_type)` 建立唯一索引，确保每种类型最多 1 间。
> - `last_rent_tick_id` 关联 `shop_tick.id`，不关联 `stock_market_tick.id`。

### 9.3 现有表复用

- **`characters`**：灵石字段已存在，收租直接增加角色的 `spirit_stones`。

### 9.4 不对现有表做任何扩展

- **`stock_market_tick`** 不被收租系统引用或扩展，两个系统的 tick 独立运行。

## 十、业务流程

### 10.1 收租 Tick 处理流程（每 30 分钟）

```
stockMarketScheduler 触发 tick
  │
  ├─ 现有流程：生成股市新闻、更新股价、记录历史...
  │
  └─ 新增流程：创建 shop_tick 记录 → 收租结算
       │
       ├─ 创建 shop_tick (status='running')
       ├─ 查询所有 shop_detail
       ├─ 遍历每间店铺：
       │    ├─ 若 last_decorate_tick_id == shop_tick.id：跳过（装修中）
       │    ├─ 计算本 tick 应得租金
       │    │    = 初始租金 × decoration_tier系数 × (1 + space_expansion × 0.5) × (1 + upgrade_level × 0.1)
       │    ├─ pending_rent += 本 tick 租金
       │    └─ 检查是否超过累积上限（48 tick）
       │
       ├─ 批量更新 shop_detail.pending_rent、last_rent_tick_id
       └─ 更新 shop_tick status='generated'
```

> **并发安全**：tick 处理使用数据库事务，确保同一 tick 不会被重复处理。通过 shop_tick.status 做幂等控制。

### 10.2 玩家主动收租流程

```
玩家点击"收取租金"
  │
  ├─ 读取店铺 pending_rent
  ├─ characters.spirit_stones += pending_rent
  ├─ shop_detail.pending_rent = 0
  ├─ shop_detail.total_rent_collected += pending_rent
  ├─ shop_detail.rent_tick_count++（记录收租次数）
  │
  └─ 检查升级：
       ├─ 计算当前等级所需经验 = 10 × (upgrade_level + 1)
       ├─ 如果 rent_tick_count >= 累计所需经验：
       │    ├─ upgrade_level++
       │    └─ 触发升级通知
       └─ 返回收取结果（租金数额、是否升级）
```

> **设计说明**：租金在 tick 时自动累积到 `pending_rent`，玩家点击"收取"只是把已累积的租金转入角色余额并触发升级判定。

### 10.3 装修调整流程（升级或降级）

```
玩家选择调整装修等级（如 玄→地 或 玄→黄）
  │
  ├─ 获取当前 tick ID
  │
  ├─ 如果是升级：
  │    ├─ 计算费用 = (目标等级单价 - 当前等级单价) × 当前面积
  │    ├─ 校验：characters.spirit_stones >= 费用
  │    ├─ characters.spirit_stones -= 费用
  │    └─ shop_detail.decoration_tier = 目标等级
  │
  └─ 如果是降级：
       ├─ 计算退款 = (当前等级单价 - 目标等级单价) × 当前面积 × 60%
       ├─ characters.spirit_stones += 退款
       └─ shop_detail.decoration_tier = 目标等级
  │
  └─ 记录装修 tick：
       └─ shop_detail.last_decorate_tick_id = 当前 shop_tick ID
       └─ 当前 tick 租金被跳过（下一 tick 处理时判断）
```

### 10.4 空间阵法扩展流程

```
玩家购买空间阵法扩展
  │
  ├─ 计算空间阵法费用
  │    空间费用 = 50 × 2^(space_expansion) × 装修等级系数
  │    装修等级系数：黄 1x / 玄 1.5x / 地 2x / 天 3x
  ├─ 计算扩展面积装修费用
  │    装修费用 = 装修单价 × 10 ㎡
  ├─ 计算扩展总费用 = 空间费用 + 装修费用
  ├─ 校验：characters.spirit_stones >= 扩展总费用
  ├─ characters.spirit_stones -= 扩展总费用
  ├─ shop_detail.space_expansion++
  ├─ shop_detail.area += 10
  └─ 返回新扩展次数和新面积
```

## 十三、关键技术决策

### 13.1 租金累积策略：Tick 时预计算，收取时转账

- **方案 A（Tick 时预算）**：每次 tick 遍历所有店铺计算租金，写入 `pending_rent`。收取时直接转账。
- **方案 B（收取时计算）**：只记录 `last_collect_time`，收取时根据时间差计算应得租金。

**选择方案 A**，原因：
1. 现有 tick 机制已存在，遍历成本高但是一次性批量处理，数据库压力可控
2. 收取操作变为纯转账，延迟极低
3. 累积上限逻辑天然支持
4. 玩家收取时体验更好（无复杂计算）

### 13.2 收租系统独立 tick

不新建定时器，在 `stockMarketScheduler` 中追加收租结算逻辑。但收租系统使用独立的 `shop_tick` 表记录 tick 事件，不与 `stock_market_tick` 混用。两个系统共享调度器但各自独立记录。

### 13.3 精度处理

灵石在现有系统中以"分"为单位（BigInt），租金计算同样遵循此规则。初始租金含 0.5 的类型（如丹药 22.5、餐饮 15）需乘以 100 后存储为整数分（2250 分、1500 分）。计算过程用整数运算，避免浮点精度问题。

### 13.4 并发安全

收取租金时需要对 `shop_detail` 行加锁（`SELECT FOR UPDATE`），防止重复收取。与现有股票交易保持一致的并发控制策略。

### 13.5 面积独立存储

`area` 字段直接存储当前面积值，而非每次通过 `初始面积 + 扩展次数 × 10` 计算。扩展空间时同步更新 area + 10，避免重复计算。
