# 持续收获作物系统 — 灵茶设计灵感

## 一、背景

现有灵田作物全部是**年度作物**（annual）：种下 → 生长 → 收获 → 枯萎/清空，一次性产出。

灵茶代表一种全新的作物类型——**永久作物**（permanent）：种下后永久存在，阶段循环，定时产出，直到玩家主动铲除。

核心差异：

| 维度 | 年度作物（灵稻/灵葫） | 永久作物（灵茶） |
|------|----------------------|------------------|
| 生命周期 | 一次性，收获后清空 | 永久，需主动铲除 |
| 生长阶段 | 线性：幼苗 → 成熟 → 枯萎 | 循环：成株 ⇄ 新芽 |
| 产出方式 | 收获时一次性发放 | 每个循环在新芽阶段采摘 |
| 元素机制 | 杂交配方 → 产生新种子 | 成株充能 → 决定茶叶品种 |
| 枯萎 | 超时自动枯萎 | 不枯萎，仅铲除移除 |

---

## 二、阶段循环状态机

### 2.1 生长阶段

```
幼苗 → 抽枝 → 成株 ⇄ 新芽
              ↑________↓
              (永久循环)
```

| 阶段 | 类型 | 行为 |
|------|------|------|
| 幼苗 | 线性 | 生长中，不可交互 |
| 抽枝 | 线性 | 生长中，不可交互 |
| 成株 | 循环起点 | 收集元素充能（记录相邻作物元素） |
| 新芽 | 循环末端 | 可采摘；根据充能元素决定产出品种 |

成株与新芽之间无限循环。每次从新芽回到成株时，清空上一轮充能状态，开始新一轮充能。

### 2.2 与年度作物状态机的统一

现有 `computeCropState()` 根据 `planted_at` + `growthStageMinutes[]` 计算当前阶段。永久作物复用这套计算：

- `growthStageMinutes` 包含所有阶段（含循环阶段）
- 成株与新芽属于"循环区间"，到达末端后回绕起点继续
- `witherAfterMinutes` 对永久作物无效（或设为 `null` / 极大值）

前端区间进度条复用现有 `StageIntervalDto[]`，无需新增 UI 机制。

## 三、元素充能机制

### 3.1 充能期（成株阶段）

成株阶段持续期间，系统记录上下左右 4 格相邻作物的元素属性，去重后存入 `charged_elements`。

示例：

```
     [金灵稻]
[水灵稻] [灵茶·成株] [火灵稻]
     [木灵稻]
```

→ `charged_elements = {金, 水, 火, 木}`（4 种元素）

### 3.2 关键时序：成株→新芽切换时做快照

**充能在进入新芽阶段时一次性结算并清空**，采摘时读取的是已结算的快照，而非实时相邻元素。

```
成株期持续中：不断记录相邻元素到 charged_elements
                          ↓
         成株 → 新芽（阶段切换瞬间）
                          ↓
    ① 快照：将 charged_elements 复制到 settled_elements
    ② 清空：charged_elements = {}（为下一轮充能做准备）
    ③ 新芽期：玩家采摘时读取 settled_elements，匹配配方
                          ↓
         新芽 → 成株（循环开始）
                          ↓
    重新开始充能，charged_elements 重新积累
```

**为什么不在采摘时实时扫描**：

- 玩家可能在成株末段有意调整相邻布局，但充能应反映"整个成株期的稳定配置"，而非最后一刻的临时布局
- 快照机制鼓励玩家在整个成株期维持合理的元素布局，而不是卡时间点换格子

**数据模型调整**：

`farm_cell` 需要两个字段：

| 列 | 类型 | 说明 |
|---|---|---|
| `charged_elements` | `TEXT[]` | 成株期实时积累的相邻元素，进入新芽时清空 |
| `settled_elements` | `TEXT[]` | 本次新芽期的充能快照（采摘判定依据） |

### 3.3 采摘判定（新芽阶段）

新芽阶段开始时，`settled_elements` 已固定。玩家点击"采摘"时，系统读取 `settled_elements` 匹配茶叶品种配方，发放对应灵材。

配方判定逻辑类似现有杂交配方（特性 + 元素条件），但结果是灵材品种，而非新作物。

### 3.3 配方示例

| 条件 | 产出 |
|------|------|
| 无充能元素 | 灵茶叶（凡品） |
| 含「金」 | 金芽茶 |
| 含「水」 | 露华茶 |
| 含「金」+「水」（相生） | 鎏金露华茶 |
| 五行全充能 | 太虚茶（稀有） |

配方结构可复用现有 `hybridRecipes` 的 `requiredAdjacent` 条件格式（`trait` / `element` / `elementCondition`），新增一个 `teaRecipes` 配置。

## 四、数据模型变更

### 4.1 作物配置（crops.json）

新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `lifecycle` | `'annual' \| 'permanent'` | 作物生命周期类型 |
| `cycleStages` | `{ start: number, count: number }` | 循环区间在 `growthStageMinutes` 中的起始索引和数量 |

现有年度作物 `lifecycle` 默认为 `'annual'`，无需迁移。

### 4.2 数据库 `farm_cell` 新增列

| 列 | 类型 | 说明 |
|---|---|---|
| `charged_elements` | `TEXT[]` | 成株阶段实时积累的相邻元素，进入新芽时清空 |
| `settled_elements` | `TEXT[]` | 进入新芽时从 charged_elements 快照，采摘判定依据 |
| `cycle_count` | `INT DEFAULT 0` | 已完成循环次数（成就/统计用） |
| `is_stored` | `BOOLEAN DEFAULT false` | 是否在暂存格子中（true = 不占生产位、无产出） |

### 4.3 DTO 扩展

`FarmCellDto` 新增：

| 字段 | 类型 | 说明 |
|------|------|------|
| `chargedElements` | `CropElement[]` | 成株期当前已充能的元素（实时变化中） |
| `settledElements` | `CropElement[]` | 本次新芽期的充能快照（采摘判定依据） |
| `cycleCount` | `number` | 已完成循环次数 |
| `isStored` | `boolean` | 是否在暂存格子中 |

### 4.4 新增配置 DTO

`TeaRecipeDto`（前端静态配置用）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `recipeId` | `string` | 配方 ID |
| `requiredAdjacent` | `RequiredAdjacentConditionDto[]` | 充能条件（复用杂交条件格式） |
| `resultCropId` | `string` | 产出的茶叶灵材 cropId |

## 五、接口变更

### 5.1 收获接口扩展

现有 `/api/farm/harvest` 需区分两种行为：

- **年度作物**：现有逻辑，清空格子
- **永久作物**：
  1. 必须在「新芽」阶段才可采摘
  2. 暂存状态（`is_stored = true`）的永久作物不可采摘，直接拒绝
  3. 根据 `settled_elements`（进入新芽时的快照）匹配配方，发放灵材
  4. 清空 `settled_elements`
  5. `cycle_count++`
  6. 不清空 `crop_id`，状态机自然回到「成株」

### 5.2 种植限制：每块灵田仅允许 1 棵活跃永久作物

种植接口需新增校验：**若玩家灵田中已存在任意活跃永久作物（`lifecycle = 'permanent'` 且未暂存），则拒绝种植新的永久作物**。

校验逻辑：
```
种植时：
if (新作物.lifecycle === 'permanent') {
  扫描当前玩家所有 farm_cell
  if (存在任意 cell.crop_id 对应作物 lifecycle === 'permanent' 且 is_stored = false) {
    拒绝："灵田中已有一棵活跃灵茶，每块灵田仅允许种植一棵永久作物"
  }
}
```

**设计理由**：
- 永久作物占据格子且不枯萎，无限数量会破坏灵田空间策略
- 限制 1 棵活跃鼓励玩家精心选择放置位置，围绕相邻元素布局
- 铲除后可重新种植（换位置或换品种）

### 5.3 暂存格子：永久作物的"仓库"

每块灵田额外挂载 **1 个暂存格子**，用于安置多余的永久作物。

**暂存格子特性**：

| 特性 | 说明 |
|------|------|
| 数量 | 每块灵田固定 1 个（不可扩展） |
| 功能 | 存放永久作物，不影响其生命周期循环 |
| 产出 | 无（暂存期间不可采摘） |
| 显示 | 独立于灵田网格，UI 上单独展示（如灵田侧边栏） |
| 取出 | 玩家可随时将暂存的永久作物取出，种回灵田（需满足"1 棵活跃"限制） |

**数据模型**：

`farm_cell` 新增列：

| 列 | 类型 | 说明 |
|---|---|---|
| `is_stored` | `BOOLEAN DEFAULT false` | 是否为暂存状态（true = 在暂存格子中） |

或者更简洁的方案：新增独立表 `farm_permanent_storage`：

```sql
CREATE TABLE farm_permanent_storage (
  character_id INT PRIMARY KEY,  -- 每玩家 1 条
  crop_id VARCHAR(64) NOT NULL,
  planted_at TIMESTAMP(6) NOT NULL,
  cycle_count INT DEFAULT 0,
  -- ... 其他永久作物需要的字段
);
```

**前端交互**：

- 灵田页面侧边栏显示暂存格子（若有作物）
- 暂存格子显示：作物图标 + 当前阶段（成株/新芽）+ 循环次数
- 操作按钮：「取出」（种回灵田，需当前无活跃永久作物）、「铲除」（永久移除）
- 灵茶种植时若已有活跃灵茶，弹窗提示"是否将当前灵茶移入暂存？"

**设计理由**：

- 玩家可能培育多棵灵茶（不同元素配置），但灵田只能有 1 棵活跃
- 暂存格子让玩家可以"换茶"而不必铲除，保留培育成果
- 无产出限制防止玩家用暂存绕过"1 棵活跃"的策略意义

### 5.4 铲除接口

现有 `/api/farm/remove` 已支持移除作物。对永久作物，语义为"铲除"：

- 清空格子（与年度作物枯萎清空一致）
- 不返还种子（永久作物无种子返还逻辑）
- 若铲除的是暂存作物，同时清空暂存位

无需新增接口，复用现有 remove 即可。

### 5.5 暂存取放接口

新增两个接口，用于永久作物在灵田格子和暂存格子之间移动：

**存入暂存**：`POST /api/farm/permanent/store`
- 将当前灵田中的活跃永久作物移入暂存格子
- 校验：暂存格子必须为空（每灵田仅 1 个暂存位）
- 设置 `is_stored = true`，记录原格子坐标（取出时可选原位或新位）

**取出暂存**：`POST /api/farm/permanent/retrieve`
- 将暂存中的永久作物取出，种回灵田
- 校验：灵田中不能已有活跃永久作物
- 参数：`targetRow`, `targetCol`（种到哪个格子）
- 设置 `is_stored = false`，更新格子坐标

### 5.6 充能结算时机

成株→新芽的阶段切换瞬间，服务端执行以下操作（在状态计算或轮询中触发）：

1. 扫描上下左右 4 格，收集相邻作物元素
2. 将结果写入 `settled_elements`（快照）
3. 清空 `charged_elements`（为下一轮成株期做准备）

采摘时只读取 `settled_elements`，不重新扫描。

## 六、前端交互

### 6.1 格子显示

- 永久作物不显示枯萎倒计时
- 成株阶段：显示充能进度条 + `chargedElements` 实时变化的元素图标（角标）
- 新芽阶段：显示"可采摘"状态 + `settledElements` 固定的元素图标 + 预计产出品种预览（tooltip）

### 6.2 操作按钮

- 采摘按钮：仅在新芽阶段显示
- 铲除按钮：永久作物始终可铲除（需确认弹窗）

### 6.3 茶叶图鉴

可考虑新增茶叶品种图鉴面板，展示已解锁/未解锁品种和对应充能条件。

## 七、与现有系统的关系

### 7.1 杂交配方

永久作物的元素充能判定独立于杂交配方系统。杂交仍然只在年度作物上触发，永久作物不参与杂交。

### 7.2 种植模板

永久作物理论上可纳入模板系统，但需考虑：

- 模板应用时，若格子已有永久作物，应跳过还是铲除替换？
- 永久作物的循环次数、充能状态是否应被模板管理？

建议初版不支持永久作物的模板种植，后续按需扩展。

### 7.3 经验系统

每次采摘仍可获得经验（与年度作物收获一致），循环次数越多，经验累积越稳定。永久作物适合作为长期稳定的经验来源。
